## 1. 当前条件与第一条任务

| 已知条件 | 对实施的影响 |
| --- | --- |
| Kinova Gen3 L53K，7 自由度，Robotiq 2F-85 | 使用本机 Kortex 接口，不能直接复用另一种机器人的动作定义 |
| Kortex Python SDK 已完成登录、状态读取；环境版本按本地记录保留 | 保留这个设备环境；模型训练环境单独建立 |
| 团队报告已有控制程序或遥操作可以取放 | 优先检查该程序并加录制，不必先训练模型才能采示范；程序位置、控制语义与日志仍待核实 |
| 旧 VLA 程序和权重无法取得 | 从官方 π0.5 基础权重与自采示范开始，不再以找回旧权重为前置条件 |
| 现有 Windows 现场电脑，具体配置在团队本地归档 | 游戏本承担采集、控制、数据处理和 Agent 开发；本地 π0.5 常规推理能力尚未验证 |
| JARVIS Robot Console 已有双路视频监看 | 可复用取流部分；同时显示不等于时间同步，仍需录制、时间戳和数据检查 |
| 云 GPU 暂按约 48 小时总预算 | 分次租用，先数据检查与短试跑，再投入正式训练；不保证任意配置都能在预算内完成 |

设备历史接入与 J2/J3 角度参考记录见 [Kortex 指南](Kinova_Kortex_Windows_从零配置与关节标定指南.md)。日常连接不等于必须重标定；历史只读结果也不替代当天的设备与停止检查。

第一条任务限定为：**从备料区抓取一种颜色的积木，放入少数指定空格**。先写清起始范围、目标位置、成功条件，再扩展回收与换色。固定相机、照明、单层桌面、同尺寸轻质积木和三分区；“A3”“屋顶”必须在图像与任务表达中具有稳定对应，模型不会仅凭名字自动知道格子坐标。

## 2. 需要补齐的模块

下面是需要实现的功能，不表示主仓库已经存在这些程序。按工作项认领，不固定 A/B/C/D 人员分工。

| 模块 | 第一轮交付 | 关键接口 |
| --- | --- | --- |
| 控制与设备桥接 | 状态读取、明确动作的受控执行、停止、错误和执行状态 | 项目实现的 `get_observation`、`send_action`、`stop` |
| 相机与场景观察 | 两路稳定图像、时间戳、网格占用、颜色与不确定项 | 最新观察及其时间、来源、场景版本 |
| 录制与转换 | 原始图像、实测状态、控制指令、任务和结果；生成检查过的训练数据 | episode、动作标签约定、数据版本 |
| π0.5 训练与推理适配 | 官方基础模型、LoRA、训练处理器和本机动作映射 | 当前子任务＋图像＋状态 → 一段有时间含义的动作 |
| 语言与界面 | 结构化编辑要求、澄清、预览、确认、取消、真实进度 | `move`、`replace_color` 等有限任务类型 |
| Harness 与 ScenePatch | 状态机、保护区、场景版本、局部修改顺序、已核验记忆和有限恢复 | 任务、补丁、请求编号、执行及核验结果 |
| 评估与记录 | 固定测试条件、全部尝试、失败分类和模型对照 | 测试清单、日志、视频、版本与指标 |

机器人适配可参考 [LeRobot 的自有硬件接入文档](https://huggingface.co/docs/lerobot/en/bring_your_own_hardware)。现有控制程序如果能独立提供日志，也可以先录原始数据、离线转换，再逐步完成标准接口。不要把机器人伪装成 SO-100/SO-101 来套命令。

模型环境与设备环境通过项目定义的数据结构衔接。云端或实验室 GPU 只处理模型推理时，现场电脑仍负责状态时效、动作节奏、停止与超时；模型网络服务不能绕过本地执行检查。

## 3. 不需要等完整 Agent 才开始采集和微调

**可以并行推进两条线：**

1. **动作线：** 检查现有取放程序 → 约定动作语义 → 加录制与双相机同步 → 回放 5–10 条 → 采集窄任务示范 → 数据转换 → π0.5 试跑 → 真实取放验收。
2. **任务线：** 用保存的桌面图片与模拟执行器，开发语言解析、场景表、局部修改、预览确认、保护规则、记忆和结果核验。

动作线开始时只需要有限任务选择、录制开始/结束、停止、超时、成功/失败/人工接管标记。完整自然语言对话、语音、复杂记忆和动态规划可以后续接入。模拟执行器返回的成功必须标为模拟，不能写成真机结果。

第一次接模型执行真机动作前，最小 Harness 应具备以下状态：待确认、执行中、核验中、成功、暂停、结果未知。每个请求有唯一编号，确认绑定具体计划版本；保护条件和执行边界用明确程序规则检查。

模型动作、控制器反馈与实物核验分别记录。控制返回成功、夹爪电流增加或手爪闭合，都不能单独证明积木已放到目标。结果未知时先查询与观察，不直接重发物理动作。

## 4. 从采集到部署的通过条件

具体字段、标签生成方法、资源和命令见 [π0.5 专题](PI05_Kinova_数据采集与微调部署指南.md)。本节只保留共同阶段门槛，避免多份文档复制命令。

| 阶段 | 通过条件 | 未通过时回到哪里 |
| --- | --- | --- |
| 设备与控制 | 现场取放、状态读取和停止一致，关节/夹爪语义清楚 | 现有程序与设备接口 |
| 录制试验 | 两路图像、状态和动作对齐，一条 episode 可完整回放 | 取流、时间戳、动作日志 |
| 标签与数据 | 明确是实际控制目标还是未来实测关节角生成的标签；单位、顺序、夹爪和边界处理正确 | 数据契约与转换器 |
| 200 步试跑 | 读数与 loss 正常，能保存，并用完整资源重新加载 | 环境、数据、配置或存档 |
| 离线与实时只观察 | 输出形状、反归一化、范围、完整动作块延迟和时效正确 | 处理器与推理适配 |
| 限定真机任务 | 按约定频率执行短窗口，停止和旧动作清理有效，实物核验可靠 | 控制适配、数据覆盖或模型 |
| 重复验收 | 在预先选定的多个初始条件下保留全部成败记录，达到事先约定门槛 | 对应失败环节 |

“根据关节角生成标签”可以采用未来时刻的实测角度作为位置目标，但不能把同一时刻状态直接复制为动作，也不能忽略夹爪接触后实测开度与关闭目标的区别。保存原始控制指令与测量轨迹，才便于以后重新生成标签。

π0.5 输出动作块，执行端必须保留每个动作的时间含义；不能把整个数组瞬间发完。停止、切换子任务或更新计划时，要同时处理策略缓存和控制器尚未执行的动作。完整动作块的计算耗时与从队列取出一个动作的耗时要分开测量。

本地部署只是待验证选项。模型加载失败、延迟过高或没有稳定空间时，先验证其他推理机器；暂时没有可持续推理资源，就先保留采集和离线结果，不把云端退租后的可用性写成已解决。

## 5. 建议节奏与 48 小时预算

总周期可先按 2–4 周安排，设备可用时段、调试与数据质量可能使工期延长。48 小时是云 GPU 的总预算，不是整个项目工期。

| 顺序 | 主要工作 | 共同检查对象 |
| --- | --- | --- |
| 第一段 | 设备与现有控制程序检查、相机固定、动作契约、最小任务与日志 | 一次有反馈和实物结果的基础控制取放 |
| 第二段 | 录制、标签转换、数据检查；任务管理使用模拟接口并行开发 | 一条可回放的同步示范与一个正确的训练 batch |
| 第三段 | 小规模租卡试跑、重载、正式微调和推理适配 | 可重载模型与限定任务的全部真机尝试 |
| 第四段 | 多步编辑、人工保护、有限恢复、独立测试和演示 | 连续协作闭环及可复现存档 |

| GPU 额度 | 用途 | 计划上限 |
| --- | --- | --- |
| 第一次 | 环境、模型资源、约 200 步试跑、存档与重载 | 4 小时 |
| 第二次 | 根据实测速率安排正式训练和验证 | 24 小时 |
| 第三次 | 部署、真机对照与必要补训共用 | 12 小时 |
| 机动 | 故障处理、最终验证、演示和备份 | 8 小时 |
| 总计 | 所有阶段共用，不随重训次数重置 | 48 小时 |

计费时间包含启动、下载、调试和空闲，不只包含训练。多卡或多实例另记录数量与费用。分次租用之间停止 GPU，利用游戏本补采、处理数据和开发；推理服务的长期费用也要单独安排。

正式训练长度依据短试跑的稳定单步耗时计算，留出重载、验证、部署和备份时间。训练无法保存、模型不能重载、动作数据错位或推理去向未验证时，先解决问题，再投入主要额度。训练 loss 下降而真机失败时先查时序、单位、相机、控制适配和失败位置，不默认继续加步数。

## 6. Agent 如何接入已验证的动作技能

VLA 首先学短技能，例如放置与回收。Harness 接收用户要求后，调用 ScenePatch 生成当前场景到目标场景的必要编辑，检查占用、材料和保护区域，再展示预览。用户确认后，每次只提交一个已支持子任务，并使用新观察核验。

场景表记录物体编号、颜色、网格、占用、观察时间和版本；任务记录保存目标、保护条件、确认计划、当前请求和已核验步骤。最初可用结构化文件或 SQLite，不要求复杂记忆系统。

人工操作采用明确的轮流回合：机械臂停止、剩余动作处理完毕，界面提示允许人工操作。操作结束重新观察，可靠变化进入历史和保护记录；变化不明时先澄清。LLM 可以解释冲突和建议方案，不能自行取消人的保护要求。

先实现一种实际恢复：暂停后待取积木被移到另一已标定位置，系统恢复时发现原位置失效，更新场景、废弃旧动作、重新规划并核验。缺料、保护冲突和反复失败可以先暂停并解释，不要求首版处理所有异常。

Agent 可以改善任务组织，但不会自动补出 VLA 没有学会的抓放能力。ScenePatch 的布局预演能检查网格占用和操作顺序，也不等于已经验证机械运动无碰撞。

## 7. 课程验收与研究比较

课程需求依据见 [原始任务要求](原始任务要求.md)。至少准备 **20 条独立测试指令**，覆盖移动、替换、区域保护、目标缺失和含糊表达；与提示词示例分开。完成至少 **10 次真机局部编辑测试**，保留每次尝试。它们是最低测试数量，不是训练示范数量，也不是成功率门槛。

每次测试记录：初始布局、任务、预览与确认、模型及 Harness 版本、执行步骤、新观察、目标达成、保护区误改、重试、额外搬运、人工介入、耗时、失败原因和视频位置。观察不清单列为结果未知，不能靠控制器返回判断成功。

分别评估语言解析、场景识别、合法性检查、动作执行与结果核验。对缺料和含糊要求，正确暂停或澄清可以算正确行为，不要求每条指令都引起动作。

课程编辑策略比较采用相同模型、视觉和机械臂接口，对照整体重排、差分局部编辑、加入人工保护的局部编辑，统计额外搬运、非目标变化和用户纠正。各组都保留必要停止与执行边界。

若研究“Agent 辅助 VLA”的价值，可进一步比较基础编排、加入记忆与规则核验恢复、加入 LLM 动态决策。固定 VLA、数据、任务、尝试预算和独立成功判断；不要把多个模块同时更换后的整体改善归因于单个模块。最低课程测试量不足时，如实标注探索性结论。

## 8. 最终交付与维护

交付包应包括代码、环境版本、设备与动作定义、基础权重来源及 revision、LoRA adapter、训练处理器和统计量、所需分词器资源、数据切分清单、测试结果与失败案例。续训另保留优化器等训练状态。复制实际检查点目录，不只复制 `last` 链接；不要把模型权重和原始视频直接提交到这个文档仓库。

由另一位成员按部署文档从关闭状态重新启动，加载模型并完成一个限定任务，补齐实际缺失步骤。正式演示前冻结相机、依赖、模型和场景。传统抓放备用程序与录像可以保留，但其作用和能力应清楚标注。

今天的优先交付是：**检查已有取放程序的动作发送点，确定标签契约，录出 5–10 条可回放示范。** Agent 开发同时推进，无需等待完整框架。
