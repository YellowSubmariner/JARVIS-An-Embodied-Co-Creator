# JARVIS 从零实现与训练部署指南

面向四人初学团队的 Kinova Gen3 实施计划
2026年11月5日

本文按模块和工作项组织，不沿用旧版固定人员分工；具体任务由团队按当前情况认领。

推进时使用配套的 [分阶段任务清单](JARVIS_分阶段任务清单.md) 认领任务、记录证据和检查阶段通过条件；具体安装与训练命令继续以本文为准。

你们有一台 Windows 游戏本，可以使用 Kinova Gen3 七自由度机械臂与 Robotiq 2F-85 夹爪，云端 GPU 预算约为两天。本指南把这两天理解为约 48 小时可用机时，优先安排为分次租用。项目总周期先按 2 至 4 周安排，第一轮正式训练前完成设备、接口和数据准备；现场设备故障和可用时段可能使周期更长。两天是 GPU 使用预算，不是项目总工期。

建议路线是：先核实现场曾经运行过的 VLA 程序；若能复现，就优先复用。若没有可以复用的完整程序，选择 SmolVLA 与 LeRobot 作为小规模微调起点，在自采的 Kinova 示范上训练。Windows 游戏本负责相机、机械臂控制和交互，优先利用它的显卡运行训练后的模型。π0.5 保留为后续候选，不在第一轮同时搭建两套训练系统。

需要训练的是机械臂完成短抓放任务的动作策略。语言理解先调用现有模型，网格识别先用颜色与标记，任务管理和记忆先用普通程序实现。这些模块都不需要你们先训练一个新模型。

本指南给出已核实的官方入口、建议的实施顺序和可运行命令的前提。文中的数量、时间分配和通过门槛是团队可采用的工程起点，不代表这台机械臂已经达到相应性能。只有完成现场验证，才能把一个步骤标为已实现。

## 1 先看清现在有什么

截至本次检查，JARVIS 主仓库根目录只有 README 与 docs，主要维护项目方案、实施指南、原始要求及 Kortex 配置记录，没有完整系统的训练、采集或自主执行入口。不要在这个仓库里寻找一个已经存在的 train.py 然后期待一条命令训练出 JARVIS。[S1]

已经有价值的资产包括：设备型号与 Kortex 访问记录；各模块的接口要求；固定网格、三色积木与局部编辑的任务设计；独立发布的 JARVIS Robot Console。Console 的现有功能是腕部相机和 Astra 全局相机监看、重连与截图。它能帮助调设备，但“看见画面”还不等于“同步录制训练数据”，也不等于“VLA 能控制机械臂”。[S1] [S2]

仓库记载操作者以前成功进行过 VLA 推理，但没有据此证明当前项目已具备稳定取放能力。首先向当时的操作者收集：代码目录与提交版本、模型名称与下载地址、启动命令、输入图像与状态格式、动作单位、机器人控制程序、成功录像。能复现就保留这条路线，避免重新搭建已经存在的接口。

尤其要先核实机械臂状态。仓库记录过 J2/J3 编码器与角度参考异常，最后的只读检查确认了当时读数与就绪状态，未替代运动精度、重复定位和重启后状态的现场验收。请由老师或熟悉设备的人确认可以开展动作实验。旧文档中的 340°、180°属于当时姿态的参考登记，不是通用姿态，不应写入日常启动脚本。[S3]

建议今天产出一张设备清单：电脑型号、Windows 版本、显卡型号与显存、内存、剩余磁盘、机械臂固件与 SDK、夹爪、两路相机名称、视频来源、急停方式、可用设备时段。把不知道的项标出来，当场逐项查清。

## 2 用最少术语理解你们要做什么

| 名称 | 可以怎样理解 | 你们要做的事 |
| --- | --- | --- |
| 代码 | 程序的结构和操作方法 | 下载框架，编写相机与机械臂适配、任务管理和界面 |
| 权重 | 模型从已有数据中学到的一组数值 | 下载官方初始权重，微调后保存自己的版本 |
| 数据集 | 带时间顺序的示范记录 | 同步保存图像、机器人状态、实际控制目标和任务描述 |
| 训练与微调 | 根据示范调整模型参数 | 从预训练权重出发，学习你们的机械臂和限定任务 |
| 推理 | 用现有权重计算下一段动作 | 每次读取新图像和状态，输出动作，不更新权重 |
| 部署 | 让模型与现场程序持续配合运行 | 装好环境、加载模型、接入动作适配并检查结果 |
| checkpoint | 某次训练进度的存档 | 保存权重、配置、处理器，续训时还需要优化器等状态 |
| episode | 一次完整示范 | 从一个明确初始状态开始，到完成一个短任务结束 |
| batch 与 step | 一批样本与一次参数更新 | batch 影响显存；step 是训练次数，不是真机动作次数 |

例如训练目标可以是“把红色积木从备料区移到指定空格”。每个时刻，输入是两张相机图像、七个关节的状态、夹爪状态与这条子任务；监督目标是操作者当时发给机器人、并经过执行端约束后的动作目标。模型学习在类似观察下产生合适的短期动作。

“把屋顶换成蓝色，窗户不动”属于多步任务。先由任务管理程序拆成旧块回收、新块放置等已支持的动作，每一步都检查实物。不能只把长指令交给 VLA，然后期待它自行拥有长期记忆、保护机制和可靠的完成判断。

微调也是训练。第一版无需从随机权重开始，无需训练一个新的中文语言模型，无需从强化学习和大型仿真入手。首轮用模仿学习：让模型模仿经过检查的成功示范。SmolVLA 内部采用的训练目标由官方代码处理，你们首先需要保证数据语义正确。[S6]

## 3 明确第一版做到哪里

第一版固定桌面、固定相机、单层网格、三种颜色、同尺寸轻质积木。设置拼图区、备料区和回收区，准备两种初始图案。屋顶、窗户等语义区域先人工标注，暂不做任意物体、任意桌面或自由堆叠。[S4]

第一条可演示任务只包含一次取放：用户输入一条明确文字指令；系统读当前场景；显示源位置和目标位置；用户确认；机器人取放；相机重新观察；系统报告实际成功或失败。先把这一条打通，再扩展三块换色。

第二条演示加入局部编辑：回收屋顶旧块，再取蓝块放到空出的格子；窗户区域一直受保护。暂停时清理未执行动作，恢复前重新观察，已经核验完成的部分不重复执行。

第三条演示加入协作：机械臂停止后，人调整窗户；程序记录前后差异并展示保护标记；用户继续要求改屋顶。再设计一个明确异常，例如暂停期间待取积木被移动到另一个已标定位置，程序发现旧计划失效，重新观察、规划并完成剩余动作。

保留传统抓放程序作为设备验证、示范生成和课程备用方案是合理的。但如果最终执行的是固定轨迹或传统控制流程，就如实写明；它可以证明接口打通，不能证明 VLA 已学会动作。课程原始任务没有强制 VLA，VLA 是团队采用的技术路线。[S4] [S26]

SmolVLA 官方教程使用约 450M 参数的基础模型，面向自有任务进行微调。这里选择它是出于你们单卡、两天预算和游戏本推理的条件，不是已经证明它对这台 Kinova 最优。官方没有替你们完成 Kinova 适配；当前核查的 LeRobot 机器人目录里没有现成的 Gen3 接口。[S6] [S7] [S8]

这里区分三种东西：公开的模型代码可以下载；公开的基础权重可以下载；与你们这台机器、相机、动作约定相匹配的训练数据与适配程序，需要团队准备。最难的部分通常是第三项。

## 5 现场电脑与云端怎样分工

推荐部署关系如下。箭头表示数据流，不表示云端直接控制关节。

```text
Windows 游戏本
  相机采集 + Kortex 控制进程 + 界面 + Harness
          | 当前图像、状态、子任务
          v
  WSL2 Ubuntu 中的模型进程或已验证的原生模型环境
          | 预测动作
          v
  Windows 执行适配器检查后，交给 Kortex 控制器
          |
          v
  新图像与实物核验，决定下一步

云端 Linux GPU
  接收已经整理好的数据 -> 微调 -> 导出 checkpoint
  仅在本地推理暂不可用时，作为限时推理备用
```

先在游戏本的 PowerShell 运行以下只读检查，保存输出。nvidia-smi 不存在时，先看“任务管理器 → 性能 → GPU”和设备管理器，确认是否有 NVIDIA 独立显卡及驱动。

```powershell
nvidia-smi
wsl --status
wsl --list --verbose
```

训练需要保存中间激活、梯度和优化器状态，通常比推理占用更多显存。因此游戏本训练吃力仍可能承担推理。但目前显卡型号、显存和实际延迟未知，不能保证。即使有 8 GB 显存，也必须用你们的两路图像与实际配置测量；4 GB 或 6 GB 更需要尽早试跑，不能等租卡结束再发现放不下。

现场 Kortex 采用仓库已有的独立 Windows 环境。记录中的成功组合是 Python 3.13.7、kortex_api 2.8.0.post5 和固定旧版 protobuf。模型环境另建，不升级或覆盖它。这样模型依赖发生冲突时，不会同时破坏已验证的机械臂连接。[S3]

如果原生 Windows 模型环境安装受阻，推荐 WSL2 Ubuntu 运行模型，Windows 继续访问相机和机械臂。符合微软要求的 Windows 与 NVIDIA 驱动可以让 WSL2 使用显卡；这不等于所有机器人框架都自动兼容。相机不必先透传给 WSL，Windows 程序可以把帧和状态发送给模型进程。[S17] [S18]

尚未安装 WSL 时，在管理员 PowerShell 中按微软文档执行安装并重启；已有正常环境则不重复安装。先用 wsl --list --online 查发行版名称，再安装所需 Ubuntu。模型环境的安装与后文云端步骤相同，均使用锁定的代码版本。

```powershell
wsl --list --online
wsl --install -d Ubuntu-22.04
```

Windows 到 WSL 的服务通常可经 localhost 访问，但要按实际网络模式验证。服务地址改变只应影响模型客户端，不应改变机器人 IP。不要把机械臂的控制端口直接暴露到公网。[S19]

## 6 租卡前要自己补哪些程序

以下文件名是建议的新建模块，不是主仓库已经存在的文件。四人应在独立开发分支中实现，小步提交，依赖与数据不要都塞进一个脚本。

| 工作项 | 建议新增模块 | 第一轮必须交付的功能 |
| --- | --- | --- |
| 语言与界面 | task_parser 与 ui | 文字转结构化任务；预览、确认、取消；展示真实进度 |
| 感知与核验 | camera_capture 与 scene_observer | 相机帧、网格占用、颜色、不确定项；执行前后核验 |
| 任务管理 | task_manager 与 scene_patch | 状态机、保护区、版本化场景、局部动作顺序、记忆与恢复 |
| 模型与执行 | kinova_bridge 与 policy_adapter | 读状态、统一动作语义、受控执行、停止、模型接入 |
| 数据采集与转换 | episode_recorder 与 dataset_converter | 同步采集、回放检查、生成训练数据 |
| 评估与记录 | evaluate 与 experiment_log | 固定测试条件、记录每次尝试、对比模型版本 |

第一步，先用现有 Kortex 环境完成“只读状态 → 在指导下的有限动作 → 停止 → 回读状态”。验收不是终端打印 OK，而是机械臂实际行为、状态反馈和现场停止一致。先使用现成的高层控制方式；初学阶段不从自行编写高速力矩控制循环开始。

第二步，固定相机安装位置与桌面。保存两路示例帧，确认不会把 BGR 当 RGB、不会把左右视角交换。建立网格坐标表，并核对桌面坐标和机器人坐标的对应。二维平面映射只能处理已假定高度的平面；夹爪、积木高度和可达范围还需要真实验证。

第三步，定义一次观察的结构：采集时间、相机帧时间、关节状态时间、相机标识、状态向量、当前任务。记录延迟和缺帧，拒绝使用明显过时的帧。两个相机画面能够同时显示，不代表它们已经和关节状态同步。

第四步，编写适配器。LeRobot 的 Robot 接口提供 get_observation、send_action、连接与断开等结构；你们要在其中接 Kortex 或本地桥接服务，并声明观察与动作特征。禁止为了通过示例而把机器人类型伪装成 SO-100/SO-101。实现思路参考官方 Bring Your Own Hardware。[S8]

第五步，语言交互与任务管理模块先用保存的桌面图片与模拟执行结果联调。可以让模拟执行器返回“成功”“抓空”“目标占用”，验证任务状态、日志和保护规则；界面必须清楚标记模拟模式。这部分不占云 GPU。

第六步，四人打通一次真实取放闭环；若 VLA 尚不具备动作能力，用已验证控制程序采集示范并验证接口，随后提前微调。不能为了等完整智能体完成而推迟动作层验证，也不能为了展示动作而跳过最小任务管理与核验。

## 7 先确定动作含义 再采数据

建议首轮讨论的动作契约是：七个关节目标位置加一个夹爪目标，共八维。状态为相同固定顺序的七个实际关节位置及实际夹爪状态。它仅在执行端已经验证支持该目标表示时采用；若现有遥操作和控制程序使用末端增量或关节速度，应结合现有控制接口统一选择，不能在录制后靠改字段名转换。

数据契约至少写清以下内容：关节顺序、角度单位、绝对位置或增量、基座或工具坐标系、夹爪值域与开闭方向、采样频率、动作持续时间、图像尺寸与颜色顺序、相机名称、时间戳对齐办法、缺帧处理、限位和停止规则。每次改变契约要改版本号。

例子：observation.state[0] 表示 J1 的实际角度，action[0] 表示下一控制周期的 J1 目标角度。二者不能都填当前实测角度，否则模型容易学成保持不动。夹爪状态最好来自反馈；若暂时只能拿到命令值，应明确其局限，不能当作已夹住物体的证据。

关节角度存在跨越 0° 与 360° 的问题。例如连续运动在原始读数中可能从 359° 变成 1°。转换、归一化和执行端必须采用同一套经过验证的连续表示或角度处理方法；不能把它理解成需要转动 −358°。动作维度相同并不能检查出这种错误。

先固定一种已验证的策略采样频率，例如以 10 Hz 作为工程试验起点；它不是机械臂底层伺服频率，也不是官方对 Kinova 的推荐值。需测量实际控制接口是否支持对应节奏，采集、训练与部署保持一致。相机可以更高帧率取流，再按时间戳选帧。

模型常输出一段未来动作，即 action chunk。不要把整段瞬间发给机械臂，也不要每到一个采样时刻都重新提交一个互相打断的阻塞运动。执行端必须负责节奏、插值或目标跟踪，并在暂停时停止和清空尚未执行的动作。第一轮使用短执行窗口，重新观察后再预测，窗口长度由实测推理时间与控制稳定性共同决定。

## 8 具体怎样采训练数据

先准备可以重复完成短任务的示教方式。优先复用实验室已有手柄、遥操作或经过验证的抓放程序。网页上点击按钮让机械臂动起来，只有在程序能同步记录真实状态与发出的动作时，才适合转换为训练数据。单独拍视频或保存抓取前后两张照片不够。

先录 5 至 10 条试验 episode。每条从机械臂等待位、积木初始位置与明确任务开始，经过接近、抓取、抬起、搬运、放置、释放，再到清楚的结束状态。保留过程中所有有效时刻； reset 和人布置桌面的片段不要混进机器人模仿的成功轨迹。

逐条回放，重点检查：动作方向是否与画面一致；抓取时夹爪标签是否闭合；状态与目标是否错位一帧或多帧；同一时间是否有两路正确图像；轨迹末尾是否确实放好；任务文本是否描述了实际动作。先修录制程序，再扩大采集，避免得到几百条无法训练的数据。

首个小实验只学习一个短任务家族，例如备料区取红块，放到两个或三个已标定目标位置。官方教程把约 50 条任务示范作为起点；这不是 Kinova 达到可靠抓放的保证。可先做 60 条有效示范，再根据失败类型补数据。[S6]

覆盖两类基本技能后再扩展数据：从备料区放到拼图区，以及从拼图区回收到回收区。换色是这两类动作的组合，不必一开始录制几十步的完整长任务。若实际还需要拼图区内移动，就单独增加对应示范。

| 采集阶段 | 建议数量 | 目的 |
| --- | --- | --- |
| 录制程序验收 | 5 至 10 条 | 检查数据字段、时序和回放 |
| 第一轮窄任务试训 | 约 60 条有效示范 | 验证模型能学习本机的动作关系 |
| 扩展到放置与回收 | 共约 150 至 300 条 | 覆盖三色、若干位置、两类任务及必要变化 |
| 针对失败补采 | 每类先补 10 至 20 条 | 修复明确缺口，再决定是否继续扩大 |

这些数量是预算内的采集规划。机械臂差异、相机视角和动作复杂度可能要求更多数据。每个重要变化都要重复示范，不能把 60 条拆成 60 个各出现一次的新任务。也不要让红块永远只出现在左边、蓝块永远只出现在右边，造成模型只记位置。

文本任务优先采用少量一致、具体的模板。中文需求由语言模块转成固定子任务文本；模型未验证中文能力前，可用英文模板。网格代号 A3 本身没有视觉意义，必须通过示范、可见标签或一致的图像目标标记让模型学到含义。所有目标标记都要在训练与推理中以同样方式生成，不能训练时输入原图、部署时突然加红框。

记录失败轨迹作为诊断材料，但首轮普通成功模仿训练不要无标注地混入错误抓放。人在中途接管纠正的轨迹应分段、标记并检查；有了适合这种数据的训练方法后再利用。相机、桌面位置、光照或夹爪配置改变时，要记录并评估是否需重新采集。

## 9 数据怎样保存和切分

每条原始 episode 单独保存：两路视频或图像序列、状态序列、动作目标序列、时间戳、任务文本、初末场景、成功标记和采集说明。原始记录保留在本地和另一份备份中，再转换成框架格式；以后换模型，就不必重新采一遍。

建议保留以下目录。目录名是你们新建的组织方案，不是框架规定的训练格式。

```text
jarvis-data/
  raw/episode_000001/
  raw/episode_000002/
  manifests/splits.json
  manifests/action_contract.json
  train/     转换后的训练集
  val/       转换后的验证集
  test/      封存的测试集
  review/    回放检查与剔除记录
```

LeRobot 数据不只是一个 MP4 文件夹：它包含结构化帧数据、视频和描述特征/episode/统计量的元数据。使用当前锁定版本的 LeRobotDataset API 转换，先检查一条数据能否读回，再批量处理。不要手写一个目录后就认为它已经符合格式。[S9]

按完整 episode 切分，例如 70% 训练、15% 验证、15% 测试；这只是起点，小数据更应按任务与位置分组检查覆盖。相邻帧高度相似，不能把同一段轨迹前后帧随机分到训练与测试。建议把部分采集时段或位置组合整体留给测试，且保证每种基础任务有足够训练例子。

训练集用于更新参数；验证集用于选择训练步数、检查点和参数；测试集用于最后评价，不拿来反复挑选模型。另准备真机测试起始布局，评价闭环执行表现；离线测试轨迹上的误差不能替代真机成功率。

将三份数据分别转换为独立数据集目录，训练只传 train 目录，让归一化统计量来自训练集。当前核查版本提供 eval_split，但仅按 episode 留出不应自动理解为全部统计量都只来自训练部分。独立目录更容易避免新手混用统计量。[S15] [S27]

训练与推理必须复用同一套输入/输出处理器及训练统计量。把动作归一化到模型容易学习的数值范围后，执行前要正确反归一化。使用错误统计量可能仍然输出八个数，却对应完全不同的实际动作。

租卡前，应能在本地读取若干随机样本，打印字段和形状，并保存图像。预期两路图像存在、状态与动作各为八维、没有 NaN、关节顺序和单位正确、任务文本与示范相符。能读出一个 batch 是数据验收，不能替代控制验收。

## 10 租什么 GPU 怎样不浪费两天

首选一张 24 GB 显存的 NVIDIA GPU 做 SmolVLA 的小 batch 微调，例如 3090、4090、A10 或 L4 对应配置。它们速度并不相同，按平台可用性、驱动与总价选择；如果 A100 的价格适合预算，也可选择。官方硬件指南把 SmolVLA 在特定 batch 配置下的显存估算放在约 10 至 16 GB，属于选型参考，不是你们两路图像配置的保证。[S11]

优先选支持 SSH、可保存持久磁盘、有足够下载带宽、能够运行锁定依赖的 Linux 镜像。建议先准备至少约 100 GB 工作空间，实际按数据视频、模型、环境和多个检查点的体积增加。系统内存可先以 32 GB 为起点；都属于工程预留，不是模型硬性最低值。确认关机、停机、释放实例分别怎样计费，数据盘是否保留，下载文件是否收费。

不要只看“CUDA 已安装”。本指南锁定的 LeRobot 代码默认 Linux 依赖采用 CUDA 13 对应轮子，安装文档列出相应驱动要求，包括 NVIDIA 驱动至少 580.65。选镜像时先核对这一点。若平台只有旧驱动，按官方 CUDA 12.6 路线重新配置并保存新的依赖记录，不能手工换完 PyTorch 后仍声称使用原 lock 文件原样复现。[S20]

本指南不提供未核实的实时租价。实际预算是 GPU 实例单价乘计费时长，再加磁盘与传输等费用。例如平台显示每小时 P 元，48 小时计算部分就是 48P 元；如果按 GPU 数量计费，还要核对是否误选了多卡实例。先租一张即可。

把约 48 小时看成总预算上限，允许分次使用：

| 批次 | 上限分配 | 工作与退出条件 |
| --- | --- | --- |
| 第一次 | 4 小时 | 安装、下载、200 步试跑、保存和重载；不通过先停机排错 |
| 第二次 | 24 小时 | 正式训练与验证；保存可比较版本，不把全部时间用于一个长跑 |
| 第三次 | 12 小时 | 游戏本部署、真机对比、必要的补采后短训 |
| 机动预算 | 8 小时 | 修复、最终验证、演示及备份；不要求全部用满 |

分次租用时，暂停之间在现场补数据、检查动作和开发软件，避免让 GPU 等人。下一次不一定能租到同一张卡，所以每次停机前都要备份。如果平台只能连续租两天，就在开机前让四个人、机械臂时段、训练数据和测试表全部就绪，按相同顺序推进，最后至少留几个小时下载结果。

租卡前检查单：

- [ ] 知道游戏本显卡型号与显存，已有本地推理试验或明确备用地点。
- [ ] 机械臂状态、停止和基础控制已由现场验证。
- [ ] 至少一条稳定相机链路已验收，正式训练所用视角已经固定。
- [ ] 动作定义冻结，录制与执行含义一致。
- [ ] 小样本回放通过，正式数据可读，train/val/test 分开。
- [ ] 训练代码版本、权重地址、磁盘位置和备份方法已写好。
- [ ] 文字任务、预览、确认、状态记录至少可用模拟执行器跑通。

如果本地模型预检查完全无法运行，可把第一次短租作为 GPU 可行性检查，先用少量已验收数据验证；不要直接订满 48 小时。

## 11 云端安装和下载的逐步命令

**以下命令基于固定版本源码核查，尚未在你们的租赁服务器与数据上执行。它们是有前置条件的实施模板，不代表本项目已经完成训练。** PowerShell 块在 Windows 运行，bash 块在云服务器或 WSL 的 Ubuntu 终端运行；不能把两种环境的命令直接混贴。

### 11.1 连接服务器并选择保存位置

租赁平台会提供服务器地址、用户名、SSH 端口和登录方法。用平台给出的实际命令连接。以下尖括号内容必须替换，不能原样执行：

```powershell
ssh -p <SSH端口> <用户名>@<服务器地址>
```

进入 Linux 后先运行 nvidia-smi，确认显示租到的卡。下面把 /data/jarvis 作为示例目录；先在平台确认 /data 是否为可用且会保留的磁盘，再改成实际位置。变量 JARVIS_ROOT 只在当前终端有效，重连后要重新设置。

```bash
nvidia-smi
df -h
export JARVIS_ROOT=/data/jarvis
mkdir -p "$JARVIS_ROOT"/{code,models,datasets,runs,backup}
cd "$JARVIS_ROOT/code"
```

### 11.2 安装锁定版本的代码

前置条件：镜像已提供 git、uv、视频解码所需的 ffmpeg 与合适的 NVIDIA 驱动。uv 是管理 Python 和依赖的工具；缺少时按其官方安装说明安装。先检查版本，不要把终端里的“command not found”当成模型出问题。[S20] [S21]

```bash
git --version
uv --version
ffmpeg -version
git clone https://github.com/huggingface/lerobot.git
cd lerobot
git checkout 9e5ee9859480e425a97a6836bb3fee479539beb5
uv sync --locked --python 3.12 --extra training --extra smolvla
uv run --no-sync python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'NO CUDA')"
```

本次核查版本要求 Python 至少 3.12。使用这里的提交版本与依赖锁，不同时照搬旧版 Python 3.10、旧数据目录和旧推理命令。最后一条应显示 CUDA 可用和显卡名称；若显示 False 或 NO CUDA，先修环境，暂不训练。

下面所有 uv 命令都在这个 lerobot 目录执行。`uv run --no-sync` 表示使用已经建好的环境，避免每次运行重新改依赖。下载失败先检查联网、磁盘和平台下载限制；不要把私人访问令牌写进脚本或上传 GitHub。

### 11.3 下载初始权重与相关资源

权重可以由云服务器直接下载。你不需要先下载到游戏本，再上传一遍。这里同时固定基础策略与它使用的视觉语言资源版本。[S7] [S12] [S13]

```bash
uv run --no-sync hf download lerobot/smolvla_base \
  --revision 5e8d12a6e2975b0e5e5fce7c8caf47c371d257b6 \
  --local-dir "$JARVIS_ROOT/models/smolvla_base"

uv run --no-sync hf download HuggingFaceTB/SmolVLM2-500M-Video-Instruct \
  --revision 7b375e1b73b11138ff12fe22c8f2822d8fe03467 \
  --local-dir "$JARVIS_ROOT/models/smolvlm2_500m"
```

第二个目录包含模型构造和文字处理会用到的资源。只拿第一个目录中的 model.safetensors 可能仍会在运行时尝试联网。磁盘文件大小也不等于运行显存：模型计算时还会占用额外空间。

为了让实际加载也使用这份固定资源，而不是重新按在线 main 查找，复制一份基础策略配置，并同时修改模型资源路径与分词器路径。保留原下载目录。下面命令在 Linux 终端完整粘贴执行；若工作副本已经存在，会停止而不覆盖。[S14]

```bash
uv run --no-sync python - <<'PY'
import json
import os
import shutil
from pathlib import Path

root = Path(os.environ['JARVIS_ROOT'])
base = root / 'models/smolvla_base'
working = root / 'models/smolvla_base_local'
backbone = str((root / 'models/smolvlm2_500m').resolve())
assert Path(backbone, 'config.json').is_file()
shutil.copytree(base, working)

config_path = working / 'config.json'
config = json.loads(config_path.read_text())
config['vlm_model_name'] = backbone
config_path.write_text(json.dumps(config, indent=2) + '\n')

processor_path = working / 'policy_preprocessor.json'
processor = json.loads(processor_path.read_text())
steps = [s for s in processor['steps']
         if s.get('registry_name') == 'tokenizer_processor']
assert len(steps) == 1
steps[0]['config']['tokenizer_name'] = backbone
processor_path.write_text(json.dumps(processor, indent=2) + '\n')
print('Training base:', working)
PY
```

### 11.4 上传数据并检查

在游戏本使用平台文件上传工具、SFTP 工具，或 scp，把转换好的 train/val/test 完整目录传到服务器的 datasets 下。上传的是包含 meta、data、videos 等内容的整个数据集，不只是视频。可在上传前后生成文件校验和，核对文件数与总体大小。

Windows PowerShell 的 scp 示例使用大写 -P 指定端口。下列路径需替换成自己的实际值：

```powershell
scp -P <SSH端口> -r "D:\JARVIS\datasets\train" <用户名>@<服务器地址>:/data/jarvis/datasets/
```

回到 Linux 终端，检查训练集描述文件：

```bash
test -f "$JARVIS_ROOT/datasets/train/meta/info.json"
du -sh "$JARVIS_ROOT/datasets/train"
uv run --no-sync lerobot-train --help
```

test 命令正常时不打印文字；如果返回非零状态，说明位置或格式需要检查。接着用团队实现的数据检查程序读若干样本并展示图像。这里不能只凭“上传成功”就跳到正式训练。

## 12 从试跑到正式训练

### 12.1 先跑 200 步

前置条件：数据已经转换为此版本能读取的 LeRobotDataset；train 目录的状态与动作定义均为八维；相机字段与数据元信息正确；基础权重本地副本已准备。下面命令只检查训练流程，不生成可保证上机的动作模型。[S10] [S15]

```bash
uv run --no-sync lerobot-train \
  --policy.path="$JARVIS_ROOT/models/smolvla_base_local" \
  --policy.input_features=null \
  --policy.output_features=null \
  --policy.device=cuda \
  --policy.freeze_vision_encoder=true \
  --policy.train_expert_only=true \
  --policy.train_state_proj=true \
  --policy.push_to_hub=false \
  --dataset.repo_id=local/jarvis_train \
  --dataset.root="$JARVIS_ROOT/datasets/train" \
  --batch_size=4 \
  --steps=200 \
  --save_freq=100 \
  --log_freq=20 \
  --env_eval_freq=0 \
  --num_workers=4 \
  --output_dir="$JARVIS_ROOT/runs/smoke_001" \
  --job_name=jarvis_smoke_001 \
  --trackio.enable=false
```

几个参数要看懂：

- policy.path 指向起始权重。input_features/output_features 设为 null，让框架依据自己的数据重建输入输出定义；否则可能沿用基础权重的六维配置。不能只把相机名称改掉就认为八维已适配。
- freeze_vision_encoder、train_expert_only、train_state_proj 明确采用部分参数微调。首轮不是 LoRA，不需要同时调一堆 LoRA 参数。
- dataset.root 是服务器上的数据目录。local/jarvis_train 在这里是本地数据标识，不要求已经在 Hugging Face 建立同名在线仓库。
- policy.push_to_hub=false 关闭训练结果自动上传；公共模型下载与自己的数据是否公开是两回事。
- batch_size=4 是显存保守起点。显存足够可再试 8，不要直接照抄别人 64 的设置。
- steps=200 用于排错。输出目录不能与已有实验混用；重试时换名字或明确续训。
- env_eval_freq=0 表示不启动框架里的环境评估；并不意味着测试已经完成。

另开一个终端观察 nvidia-smi；确认 GPU 在工作、显存没有溢出。检查 loss 是有限数而非 NaN，训练时间没有主要耗在加载损坏视频上，检查点实际写入磁盘。特别检查新 config 中 state/action 的真实维度及相机名，再加载该检查点处理一份录制观察。

### 12.2 通过试跑后才做正式训练

首轮可以把 10,000 至 20,000 步作为候选范围，不把数字当作必须完成的指标。先测稳定后的每步耗时：假设每步约 1 秒，20,000 步仅更新部分约需 5.6 小时，再加保存和评估；如果每步 3 秒，就已超过 16 小时。这个例子是算时长的方法，不是实测结果。

在上一个命令基础上，正式实验改为新的 output_dir/job_name，并调整以下参数。不要仅运行这个片段，它是对完整命令的修改说明：

```text
--steps=20000
--policy.scheduler_decay_steps=20000
--save_freq=2000
--output_dir=实际JARVIS_ROOT/runs/run_001
--job_name=jarvis_run_001
```

学习率衰减长度应与实际计划步数协调。第一轮保持其余官方默认值，先只调整 batch、步数与保存频率。100 或 200 步试验中的优化状态不必带到正式实验；另开正式 run 更容易比较。

长训练可用 tmux 保持终端会话，避免本地 SSH 断开直接终止进程。服务器本身关机时 tmux 不能让训练继续。若镜像没有 tmux，先安装或使用平台明确提供的任务运行方式。

```bash
tmux new -s jarvis_train
```

在会话中运行完整训练命令；按 Ctrl+B 后按 D 离开会话，使用 tmux attach -t jarvis_train 返回。每次训练记录代码提交、数据版本、初始权重、参数、起止时间、显卡和检查点位置。

### 12.3 怎样知道训练有没有用

上面的训练命令只读取训练集，日志里的 loss 不是验证集成绩，更不是抓放成功率。还要实现离线验证程序：读取独立 val 数据，使用训练检查点保存的预处理/反归一化，在固定条件下计算辅助误差或损失并查看预测动作。不要改用验证集自己的统计量。

离线误差改善但真机仍失败时，优先排查图像和状态错位、动作单位、夹爪映射、控制节奏、相机角度变化，以及训练数据是否覆盖该初始位置。继续增加训练步数通常不能修好错误的动作映射。

候选版本进入真机前，先做离线与实时不执行检查。测试使用同一批预先保留的布局，记录每次尝试。基础模型若尚不能安全接入八维 Kinova，只做离线兼容性检查，不为凑“微调前后对比”强行执行未经验证的输出；可以先建立一个经过适配和短训的可用基线，再比较后续改进，并准确命名。

### 12.4 中断后怎样继续

LeRobot 检查点中，pretrained_model 用于保存策略、配置和处理器；同级 training_state 保存续训所需的优化器、随机状态等。下面仅适用于所示完整检查点确实存在的情况，数字目录按实际保存结果替换：[S15]

```bash
uv run --no-sync lerobot-train \
  --config_path="$JARVIS_ROOT/runs/run_001/checkpoints/004000/pretrained_model/train_config.json" \
  --resume=true
```

换服务器后要核对 train_config.json 里的数据、输出和 backbone 路径，必要时按当前目录覆盖。只拿到 model.safetensors 无法原样恢复优化器进度。不要把重新从模型权重开始训练，与精确恢复一个中断实验混为一谈。

## 13 把训练结果部署到游戏本

### 13.1 先打包 再退租

至少带走以下内容：

| 文件或目录 | 推理是否需要 | 为什么保留 |
| --- | --- | --- |
| 选中检查点完整 pretrained_model | 需要 | 权重、配置、归一化处理器、分词器等 |
| 对应完整 training_state | 续训需要 | 恢复训练进度与优化器 |
| 固定版本的 backbone 目录 | 本指南加载方式需要 | 保证模型构造与资源可离线加载 |
| 代码提交与依赖锁 | 需要 | 重建同一套软件环境 |
| Kinova 适配代码与动作契约 | 需要 | 解释模型输出并落实到机械臂 |
| 相机和标定配置 | 需要 | 保持观察与动作的对应 |
| 数据版本清单、训练日志和评测记录 | 复现需要 | 知道模型怎样训练、有什么限制 |
| 原始数据与转换后数据 | 后续训练需要 | 补采、修转换或换框架时复用 |

有的 last 是符号链接。跨 Windows 备份时不要只复制一个指向服务器旧路径的链接，要复制它实际指向的数字检查点目录。备份后在另一位置重新加载，确认不是只有文件名而缺少内容。

可在 Windows 用 scp 拉回完整的真实检查点目录；以下为路径模板。模型资源目录也按同样方式复制：

```powershell
scp -P <SSH端口> -r <用户名>@<服务器地址>:/data/jarvis/runs/run_001/checkpoints/004000 "D:\JARVIS\checkpoints\"
```

基础权重是公共资源，通常可以重新下载；你们自己微调的检查点、数据和适配代码更不可替代。建议游戏本之外再保存一份到移动硬盘或团队持久存储。没有必要把大权重塞进普通 Git 提交。

### 13.2 游戏本加载模型前做路径整理

推荐沿用第 5 节的分进程方式：Windows 运行相机与 Kortex，WSL2 运行锁定的模型环境；如果已经验证原生 Windows 可运行，则可以保留该方案。先在模型环境跑 CUDA 检查，确认不是意外退回 CPU。

训练配置里可能保留云服务器的绝对 backbone 路径，例如 /data/jarvis/models/smolvlm2_500m。把部署副本的 config.json 中 vlm_model_name 改成游戏本实际可访问的完整目录，例如 WSL 中的 /mnt/d/JARVIS/models/smolvlm2_500m。保留云端原始检查点不动，另存部署副本。[S14]

当前版本新检查点可包含随保存带走的 tokenizer 子目录及相对引用；完整保留它们，不随意删掉。若实际配置仍引用在线模型 ID，也需要按本地资源整理并验证。只改 backbone 一处路径不必然解决全部依赖。

在有网络时先成功加载，再用离线模式完整重启一次。此时仍要启动模型而不是只检查文件存在：

```bash
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
```

设置后运行已实现的离线检查入口，确认不联网也能处理保存的观察并输出动作；这两个环境变量本身不会启动模型。未通过时补齐具体缺失资源，不能把“已经下载权重”当作离线部署完成。

### 13.3 需要实现的推理循环

以下是流程示意，不是可以直接执行的 Kinova 控制代码：

```text
加载策略和 checkpoint 中的输入输出处理器
等待 Harness 提交一个已确认的当前子任务
读取新鲜、对应同一时段的图像与机器人状态
预处理 -> 模型预测 -> 动作反归一化
检查维度、单位、限位、请求编号和场景版本
若仅观察模式，则只记录预测，不发送运动
否则执行经过验证的短窗口动作
重新观察并按需要继续预测
暂停或子任务切换时，清理旧预测和未执行动作
动作阶段结束后，由视觉模块核验，再由 Harness 形成完成结论
```

当前 LeRobot 部署入口包含 lerobot-rollout，远程推理入口包含 lerobot-policy-server。但本项目没有现成的 --robot.type=kinova_gen3 命令；这个类型只有在你们完成、注册并验收对应适配器后才成立。不应抄 SO-101 的串口和机器人选项。[S22]

先用保存观察测量完整动作块推理时间、峰值显存，再接实时相机测端到端延迟。不能只测从模型缓存队列取出一个动作的时间，它可能远小于真正计算一次的时间。记录平均延迟与较慢情况下的延迟，确保执行窗口与实际推理节奏匹配。

验证顺序：离线录制数据 → 实时图像但禁止动作发送 → 现场指导下的限定短任务 → 多步取放 → 暂停续接 → 人工保护和受控恢复。每一层留下记录，失败时退回对应层排查。

### 13.4 如果游戏本真的跑不动

先核对是否正确使用独立显卡、后台程序是否占显存、图像与模型配置是否一致。不要临时随意删相机或换量化模型后直接接机器人；输入或数值精度改变需要重新验证。

可用的备用路线是实验室局域网另一台 GPU 电脑，或者在预留的租卡时间内运行云端推理。云端收图像与状态、返回预测动作，现场程序保持控制权并处理超时。云 GPU 退租以后，这条服务也就停止；如果本地或实验室没有可用算力，长期使用需要额外推理资源。

官方远程部署示例仍需要你们修改八维状态/动作、两路图像、模型路径和动作语义，并实现要求的机器人能力。特别是保持位置的语义不能靠把标志设成 True 来“通过检查”；重复速度命令不等于保持位置。服务器与现场之间用可信网络或 SSH 隧道，现场独立处理断线、停止和过期预测。[S23]

## 14 按四周安排实施工作

下面是零基础团队的建议节奏，不是保证四周完成。设备状态、已有代码、每周能使用机械臂的时间会显著影响进度。以每周的验收结果决定是否继续，云 GPU 的 48 小时分散嵌入其中。

| 时段 | 主要工作 | 共同验收结果 |
| --- | --- | --- |
| 第 1 周 | 文字指令格式与模拟任务闭环；相机、网格、Kortex、已有 VLA 与停止功能检查 | 设备清单、动作契约、一次接口闭环 |
| 第 2 周 | 适配器、录制器、转换器；同步采集与回放；预览、确认、保护规则与记忆 | 小样本通过，采集窄任务数据，完成第一次短租试验 |
| 第 3 周 | 正式微调与独立验证；游戏本部署；多步规划、暂停续接和局部编辑 | 可重复的单动作 VLA 闭环，扩展至局部换色 |
| 第 4 周 | 对失败补采与必要短训；语音、人工变化保护、至少一种恢复和策略比较 | 独立测试、完整日志、版本冻结、演示与备份 |

这些是工作顺序，不是固定的人员分配。设备和模型调试期间，语言交互、界面与任务管理可以先用图片和模拟接口推进；动作层可以用固定短任务独立验证。团队共同参与示范采集、数据回放与最终测试，按当前设备时段和进展认领工作。

阶段进入条件可以这样定：能够稳定读取并解释数据，才开始正式训练；能够离线重载并解释动作，才接真实动作；单动作没有可靠结果，先缩小任务并排错，暂不增加长任务复杂度。项目范围可以缩小，但未经验证的能力不能标为完成。

## 15 为什么本轮不优先从 π0.5 开始

如果找回的现场程序本来就是已适配的 π0.5，当然先复用。这里的建议是避免没有任何程序和数据的团队，同时搭建 SmolVLA 与 π0.5 两套系统。

openpi 官方代码为 https://github.com/Physical-Intelligence/openpi，本次核查提交是 215abfb217dbac7d5f1273282331b9b1866c0479。基础权重为 gs://openpi-assets/checkpoints/pi05_base；pi05_droid 是 DROID 专用版本，pi05_libero 是仿真任务版本。它们都不是已验证的 Kinova 成品。[S16]

官方 openpi 的一般显存估计为推理超过 8 GB、LoRA 超过 22.5 GB、全量微调超过 70 GB；这些数值随配置变化，不能直接承诺游戏本或任意 24 GB 卡适用。当前 PyTorch 路径不支持 LoRA；若选这条低内存路线，需要核对 JAX 配置，不能搜索到一个名字就假设存在“π0.5 Kinova 一键 LoRA 训练”。[S16]

当前代码没有可直接采用的 pi05_libero_low_mem_finetune 配方；Kinova 仍需要自己的输入/输出映射、数据转换、训练配置和统计量。openpi 还锁定较早的 LeRobot 依赖，所以应独立环境，保留原始示范以便转换。新 LeRobot 的 v3 数据不能未经检查就认定兼容。[S24]

另外，官方 DROID 完整训练示例的“两天”指 8 张 H100，数据约需 1.8 TB。它不等于你们租一张 GPU 两天就能完成同样工作。你们本轮应该做小范围自采数据微调，不下载整个 DROID 从头铺开。[S25]

如果后续确实选 π0.5，先安排一个独立的可行性验证任务：固定 Ubuntu 环境、选择基础权重、确定动作表示、实现 Kinova 数据与策略映射、计算自己的训练统计量、100 至 200 步试跑并重载，再讨论长训练。本指南不提供一个不存在的 Kinova 配置名称让新手复制后报错。

## 16 最后如何验收才算实现

先分别测语言、观察、动作和完整任务，避免只看一段顺利录像。仓库要求至少 20 条独立测试指令与 10 次真机局部编辑；它们是测试数量要求，不是训练样本数量，也不代表自动达到某成功率。[S4] [S26]

20 条指令可以先按每类 4 条组织：移动、换色、区域保护、目标缺失、含糊指代。它们应与提示词示例分开，包含两种初始图案。目标不存在时正确拒绝或澄清，也是一种正确行为，不能把“没有执行”一律计为失败。

至少 10 次真机编辑记录初始布局、请求、预览、确认、每步执行、最终观察和结果。对动作任务，只有目标达成且保护区域没有误改才算成功。观察不清单独记录为未确认，不凭控制器返回成功就判定完成。为了研究比较，往往还需要更多匹配任务和重复试验，最低 10 次不能支撑所有模型和机制的充分对照。

每次尝试至少记录：任务编号、模型版本、Harness 配置、是否正确解析、是否正确识别、目标达成、保护区域误改、额外搬运、重试、人工介入、耗时、失败原因与视频位置。保留全部尝试，不只选成功案例。

比较 VLA 改进时，固定 Harness、视觉、控制边界和测试条件；比较记忆与恢复时，固定 VLA 与外部成功判断。基础编排、记忆、恢复、模型微调同时改变后，只能说整体系统变化，不能把效果全部归因于某一个模块。

建议先验证一种恢复：机器人在动作边界暂停后，由人把待取块移到另一已标定位置；恢复时先重新观察，更新场景，废弃旧动作，重新规划后完成。缺料和保护冲突先做清楚的暂停与解释，不强求机器人自行处理所有异常。

为了在有限时间内答辩，冻结一个最可靠的版本，提前一天完成整段排练。正式演示不临时更新依赖、不更换相机位置、不换没验收的模型。保留一个明确标注为传统抓放的备用版本，以及演示录像；它们的作用和实际能力应如实说明。

## 17 常见问题先按这个顺序查

| 现象 | 优先检查什么 |
| --- | --- |
| 能开相机页面但录制失败 | 是否有供程序读取的帧接口、时间戳、权限和稳定取流 |
| CUDA 显示 False | NVIDIA 驱动、当前 Python 环境、PyTorch 是否装成 CPU 版、WSL GPU 是否可见 |
| 显存不足 | batch、图像数量和尺寸、后台占用、是否意外训练全部参数；先保留原实验记录 |
| 训练慢但 GPU 利用低 | 视频解码、磁盘与数据读取；增加 GPU 不一定解决 |
| 数据维度不匹配 | 是否仍沿用 base 六维配置、相机 key 是否一致、八维顺序是否正确 |
| loss 下降但机械臂不动 | action 是否误填成 state、动作是否被执行端拒绝、单位与反归一化是否正确 |
| 动作方向很奇怪 | 度/弧度、绝对/增量、坐标系、关节顺序、0/360°跨界、夹爪开闭定义 |
| 离线好 真机差 | 时间错位、相机角度/光照变化、起始条件超出数据、控制频率与延迟 |
| 换电脑后找不到资源 | 云端绝对路径未改、处理器/分词器/backbone 没完整复制 |
| 网络断开还继续动作 | 本地超时和旧动作队列处理未正确实现，先退回仅观察模式检查 |
| 抓放成功但改了保护区 | 规划、执行边界和最终核验不完整，不能只靠任务提示语 |
| 训练两天仍不成功 | 停止盲目加步数，回查硬件、契约、同步、数据覆盖和实际失败位置 |

完成这些后，下一次共同检查的对象应该是“一条可以回放的同步示范”和“一个最小任务闭环”，而不只是更多模型介绍。此时再根据实际数据和显卡情况启动第一次短租。

## 附录 A 数据转换接口示意

下面只说明如何把已经录好、检查过的数据写入 LeRobot 格式。episodes 需要由你们的原始数据读取程序提供；这里没有连接机械臂，也不是可直接录数据的完整程序。fps=10 对应第 7 节的工程示例，实际必须改成已经验收的统一采样频率。每帧图像是 RGB uint8，状态与动作是 float32 八维。[S9]

```python
from lerobot.datasets.lerobot_dataset import LeRobotDataset

names = [f"joint_{i}.pos" for i in range(1, 8)] + ["gripper.pos"]
features = {
    "observation.state": {
        "dtype": "float32", "shape": (8,), "names": names},
    "action": {
        "dtype": "float32", "shape": (8,), "names": names},
    "observation.images.top": {
        "dtype": "video", "shape": (480, 640, 3),
        "names": ["height", "width", "channel"]},
    "observation.images.wrist": {
        "dtype": "video", "shape": (480, 640, 3),
        "names": ["height", "width", "channel"]},
}

ds = LeRobotDataset.create(
    repo_id="local/jarvis_train",
    root="/data/jarvis/datasets/train",
    fps=10,
    robot_type="kinova_gen3",
    features=features,
)
for episode in episodes:  # 由你们实现的原始数据读取器提供
    for frame in episode:
        # frame 包含上面四个字段，另有 task 字符串
        ds.add_frame(frame)
    ds.save_episode()
ds.finalize()
```

robot_type 字符串在这里是数据说明，不会自动安装机械臂驱动。train、val、test 分别转换，不能将同一 episode 放到不同集合。源视频乱序、采样不均匀或控制延迟过大时，应先修复或剔除，不能只在 fps 字段填一个数掩盖问题。

## 附录 B 四人先约定一个最小接口

下面是建议的业务字段示例，需要团队实现，不是 SDK 自带协议。Harness 给执行模块的是当前短任务，保留请求编号和场景版本；执行模块不直接接收“随意执行整段用户对话”的权限。

```json
{
  "request_id": "task_001_step_02",
  "scene_version": 17,
  "operation": "pick_place",
  "object_id": "red_03",
  "source_cell": "supply_A2",
  "target_cell": "recycle_B1",
  "protected_cells": ["window_C2", "window_C3"],
  "confirmed_plan_id": "plan_001",
  "status": "ready_for_execution"
}
```

执行适配器将这些业务信息转为经过训练验证的短任务表达；格子名称不能直接替代前文要求的视觉目标表示。执行模块返回 accepted、running、stopped、controller_done、error 或 unknown 等状态。controller_done 只代表控制阶段结束；视觉模块重新观察，Harness 核验目标和保护要求后，才能记录 task_succeeded。

Memory 首版用 JSON 文件或 SQLite 即可。至少保存当前目标、保护格、观察场景版本、确认的计划、已核验步骤、进行中请求、人工修改事件和失败记录。场景版本变化后，先检查旧计划是否仍成立；结果未知时先查询与观察，不重复发送同一物理动作。

ScenePatch 在场景副本里依次检查“旧块能否回收、目标格是否空、新颜色库存够不够、是否涉及保护区”，并生成预览。这个逻辑检查不能证明运动轨迹没有碰撞。执行适配模块还要结合机械臂、夹爪与积木几何，落实经过现场验证的运动边界；视觉模块在执行后检查是否实际误动了保护部分。
